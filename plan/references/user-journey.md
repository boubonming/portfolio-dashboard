# Portfolio Dashboard — human-usability contract

**Status:** Proposed audit/remediation design; not implemented or owner-accepted. Independent review required. This is the canonical interface contract for this audit, not a replacement whole-project roadmap.
**Verdict:** **usable with material friction** on desktop; the current narrow-screen and mutation-recovery defects prevent calling the routine workflow good.
**Human job:** A private owner opens Holdings, checks which exact lots and values are trustworthy, refreshes when needed, records or archives a lot safely, and reads evidence-backed advisory reviews without confusing feedback with a trade or scheduled analysis.

## Discord-readable journey

- **Sign in → Holdings.** Keep the current holdings-first entry. Show valuation time/status, not just numbers. Empty portfolio: **No holdings yet → Add holding**. A search with no result instead offers **Clear filter**.
- **Scan → sort/filter → inspect.** Keep exact-lot rows, original currencies and Gain/Loss/Break-even cues. On a phone, navigation stays usable and the investment remains identifiable while the table scrolls. Tiny nonzero amounts must not look like zero; **Show exact amounts** exposes full precision.
- **Refresh prices → read the outcome.** Complete and incomplete outcomes are different. **View refresh details** explains missing quotes/FX/provider failures; **Open Market Data** leads to existing setup. No complete total or allocation is invented.
- **Add holding / Archive holding → recognizable receipt.** A confirmed write remains confirmed if reloading Holdings fails. **Retry loading holdings** repeats a read, not the write. An unconfirmed write instead offers **Retry same save** or **Retry same archive**, with the identical request identity.
- **Market Data → inspect candidates → confirm every exact mapping → Save all mappings.** Late discovery cannot replace an owner's edits. Keep the atomic whole-batch rule, show what is unfinished, preserve confirmed success, and provide **Reload setup** after a conflict. Provider secrets stay outside the UI.
- **Reviews → find current/outdated/incomplete → inspect facts, opinion and sources → Record feedback.** **Back to holdings** actually returns there. Feedback remains append-only; requesting another review does not schedule one.
- **Activity → read what happened → Load more activity. Settings → configure scheduled refresh → Save schedule.** A custom cron remains custom; saved, disabled, active and degraded are distinct states. No endless loading message after a completed failure.

```text
PROPOSED — existing views, not new routes
[Portfolio Dashboard]                       [Sign out]
[Holdings] [Overview] [Activity] [Reviews] [Market Data] [Settings]

Holdings                                  [Add holding]
Valuation: Incomplete · As of [time + timezone]
Some exact lot values are usable; portfolio totals are withheld.
[Reporting currency: MYR v] [Filter holdings________] [Clear filter]
[Download CSV] [Refresh prices] [Show exact amounts]
[Refresh outcome and recovery, when available]

[Instrument / lot context | Quantity | Costs | Prices | P/L | ... | ⋮]
At 320px: wrap controls; bounded keyboard-scrollable table;
keep instrument identity visible, do not scroll the whole page sideways.
```

## Actual surface and action inventory

There is one React shell, no frontend URL router: six in-memory view values `overview`, `holdings` (initial), `activity`, `reviews`, `market`, `settings` (A:479–480, 956–963). Visible tab text is **Overview / Holdings / Activity / Review / Market Data / Settings**; accessible Review label is **Reviews**. Browser refresh resets view/filter/currency state. The brand link targets `#portfolio-content`, not a separate home route. Directly invented `/holdings` or `/settings` URLs are not part of this proposal.

- Public/session: **Checking your session…**, **Sign in**, **Sign out**. API `/api/v1/auth/session` GET, `/login` POST, `/logout` POST.
- Holdings: Reporting currency (MYR initially; MYR/USD/SGD/JPY options), free-text Filter holdings (blank), Download CSV, Refresh prices; sortable headers; Add holding dialog; each lot has Open thesis, View reviews, and ⋮ → Archive holding → explicit confirmation. No edit, sell, restore, broker sync or trade capability is presented. The standalone archive picker is a component fallback, **not rendered by App's normal children path** (H:751–768).
- Overview: portfolio valuation status, total only if complete, as-of/version, complete allocation bars/text tables or coverage warning. No currency control on this view currently; it uses the selection from Holdings. No refresh action here currently.
- Market Data: readiness badges, automatic provider discovery on entry/reload, candidate radio choices, editable provider/exact identifier/currency/provenance, row confirmation, Save all mappings. No credential-entry UI or routine refresh button. API setup GET, discover POST, mappings POST under `/api/v1/portfolios/{portfolioId}/market-data`.
- Reviews: portfolio list or exact-lot filter from Holdings, Load more reviews, View review details, Close review detail, Back to overview (currently returns Holdings), feedback decisions and optional note, Record feedback/Retry feedback. Server list supports `status` and `outdated`; current UI only sends `holding_id`, limit and cursor. No “run analysis” endpoint/button.
- Activity: read-only newest-first timeline, Load more activity and retry. No user-facing undo/restore path.
- Settings: schedule GET/PUT at `/market-data/schedule`, Enable scheduled refreshes, Daily/Weekdays/Custom cron, time/cron, timezone, optional reporting currency, Save schedule/Reload. Schedule is not a Market Data subform.
- Thesis is an in-shell per-lot editor, not another tab/route: summary, intended holding period, optional allocation limit, dynamic reasons/risks/conditions/sources, Save thesis, Cancel/Close thesis, View/Refresh revision history and explicit conflict reload.
- Shared reads/writes: overview GET and CSV GET; holding POST and exact-lot DELETE; thesis GET/PUT/history GET; review list/detail GET and feedback POST. Snapshot/review submission machine APIs are not browser actions to add.

## Findings and priority

Severity: **P0** = confirmed high-consequence trust/recovery defect; **P1** = material task failure or misleading routine interpretation; **P2** = bounded discoverability/friction; **Optional** = preference/new workflow requiring acceptance. A source-confirmed control-flow defect need not be reproduced against real private data to count as confirmed; unexercised consequences are distinguished below.

### F01 — Confirmed writes lose their outcome; uncertain holding retries can change identity (P0)
- **Task/frequency:** every successful Add/Archive uses overview reload; uncertain network/server failures are conditional but consequential.
- **Evidence:** H:568 awaits App's `onRefresh`; A:569–601 sets `state=loading`; A:997–1013 unmounts H. H:267–324 clears attempt/authority on unmount, before success/status/focus can settle. H:570 also wrongly requires the new overview revision to equal the older receipt exactly. H:556–557 discards attempts for all non-OK responses; edits change targetSignature (H:534–538). This can replace a key after an unresolved outcome. **Fixture-observed:** validated synthetic archive receipt + successful overview read removed only lot 1, left lot 2, but no archive success status survived and focus fell to body. Actual duplicate creation or server 5xx-after-commit was **not** reproduced; it is the safety risk to regression-test, not a claimed production incident.
- **Fix:** session-owned draft/attempt/validated receipt outside the loading subtree; independent confirmed-write and read-refresh states; exact retry barrier. See J3, U-05–08. Preserve server guards, not a weaker success heuristic.

### F02 — Narrow layout and table orientation break down (P1)
- **Task/frequency:** each 320px visit and every horizontal table scan; wide desktop tables also overflow their region.
- **Evidence:** A:966–975 responsive shell; 1016–1027 min-width 1250 table with action columns at far right. C:98 adds overflow but no sticky instrument rule; no named focusable Holdings scroll region. **Fixture-observed at 320px CSS viewport:** root client width 305 including desktop scrollbar, scroll width 856; Holdings region client 268 / scroll 1510; instrument position `static`, region tabIndex `-1`. Market view root overflow also occurred. These are measurements of this fixture, not universal target values. Navigation width collapsed in the fixture. Do not prescribe a guessed single CSS root cause; inspect actual MUI responsive composition.
- **Fix:** shell controls/nav reflow without document-wide overflow; bounded, named, keyboard-scrollable table and stable instrument identity. Retain the table, do not build a second mobile app. U-02/03.

### F03 — Holdings hide time/coverage context and cannot distinguish first-run empty from filtered empty (P1)
- **Task/frequency:** every daily scan, especially after missing quotes, refresh or first start.
- **Evidence:** `freshness.market_at`/`age` exist (A:42–46), but row renders only raw flags/source (1026). Snapshot time/status only appears on Overview (1001–1011); source “ok” does not tell the owner when a price was observed. Empty table always says **No holdings match this filter.** (1031), even with zero active lots and blank filter. Overview honest withholding is good but gives counts/no in-app next action; its warning omits future dependencies in copy despite displaying the count. **Fixture-observed:** incomplete Holdings shows Withheld without a valuation banner, and no quote timestamp despite supplied market_at.
- **Fix:** visible compact valuation context and per-lot source time; explicit empty/no-match; actionable Overview guidance. Do not relabel completeness as wall-clock freshness or “up-to-date.” U-01/04/09/10.

### F04 — Rounded display can make a nonzero price/P&L look zero (P1)
- **Task/frequency:** lots whose monetary magnitude is below display precision, or comparing close prices.
- **Evidence:** A:160–179 rounds every money string to ≤2 decimals; P/L cue uses exact value (217–247). **Fixture-observed:** exact `0.00125` USD P/L rendered Gain icon + `0 USD`; price `10.0001` rendered `10`. Tests deliberately assert the current two-place formatter (App.test.tsx:655 onward); changing it needs intentional test updates, not float conversion.
- **Fix:** keep compact formatting for ordinary amounts; display signed `<0.01` / `−<0.01` for nonzero magnitude below 0.01 (including currency), never numeric zero. **Show exact amounts** reveals original strings for monetary table values and changes to **Use compact amounts**. Explain “Compact amounts are rounded; sorting uses exact values.” Exact zero remains zero/Break-even. U-04.

### F05 — Settings misrepresents complex cron and has incomplete recovery (P1)
- **Task/frequency:** opening a valid step/list/range cron, re-enabling a saved disabled schedule, any GET failure/degraded state/conflict.
- **Evidence:** S:11–15 recognizes Daily/Weekdays using only last three fields; S:85 builds invalid time strings for `*/30 5 * * *`. **Fixture-observed:** this accepted-format custom expression becomes Daily with blank local time. S:185 shows Loading schedule whenever schedule=null, including after completed GET error; degraded 200 state disables writes with “Retry” copy but no Reload button unless another error exists. Disabled cron is empty by contract, currently becomes Custom cron with blank field. 412 auto-load clears edits/message (S:161–166, 72–86). Server uses strict cron parser/IANA timezone (config:76–112), not just five token counting.
- **Fix:** preset only for single bounded numeric minute/hour + exact daily/weekdays suffix; retain all other expressions in Custom cron unchanged. Explicit read states, always reachable **Reload schedule** for error/degraded, deliberate stale-settings adoption. U-17–19.

### F06 — Selected navigation can disagree with content, or yield a blank destination (P1)
- **Task/frequency:** Settings/Reviews after initial overview failure; switching tabs while thesis is open; review back navigation.
- **Evidence:** A:1040–1041 condition Settings/Reviews on data but show loading/error only for Holdings/Overview (980–995). A:979 thesis branch suppresses the selected view, while tab handler 971 changes view without closing thesis. R:397 “Back to overview” invokes A:904–912 which sets Holdings. **Fixture-observed:** Settings after initial overview 500 renders header only; selecting Settings with thesis open leaves thesis heading/content under selected Settings tab. App.test.tsx:386–414 explicitly tests the misleading Back label returning Holdings.
- **Fix:** visible recoverable data prerequisite on every dependent destination, not silent blank; dirty-thesis safe navigation and accurate selected tab; rename back button **Back to holdings**. U-11/12/15.

**F06 related recovery defect — thesis save outcome (P1, conditional):** T:415–419 asserts **The thesis was not saved** on network/response failure, although a commit may have preceded the lost response. The owner may then change a draft believing there is no recorded revision. This is source-confirmed misleading uncertainty copy, not a reproduced database incident. J1b/U-12 require truthful unconfirmed copy and unchanged-document/expected_revision retry; `internal/store/thesis.go` provides request-hash replay before revision-conflict checking. No extra thesis/history service is needed.

### F07 — Market setup can replace edits and erase success; conflict copy has no matching control (P1)
- **Task/frequency:** manual edits while discovery is pending; every successful save; stale setup save.
- **Evidence:** M:69–85 applies a late exact candidate over current draft with no touched/version check. `load()` resets all drafts/message (56–65); save sets success then immediately calls load (136–138), so success is cleared. 412 tells owner to reload (142) but normal ready surface offers no Reload setup. Save eligibility requires every instrument (116), matching Store:151–152; this is an existing intentional contract, not permission to silently save a subset. M:164 displays only some candidate evidence in choices, although exchange/region/type are available in API.
- **Fix:** touched-row guard; preserve success through a separate read reload; explicit discard-aware Reload setup; pending/remaining-row explanation and complete candidate identity. Preserve whole-batch atomicity and explicit confirmation. U-13/14.

### F08 — Review discovery/evidence require unnecessary internal knowledge (P2, material review-workflow remediation)
- **Task/frequency:** finding current/outdated/incomplete advice, understanding a multi-lot scope or a fact's support.
- **Evidence:** R:353 only supplies holding_id; O:424–425 and server parser support status/outdated already. R:340/397 foreground full lot IDs; R:296 cites evidence IDs but R:297 does not label entries with those IDs or fact anchors and omits `published_at` despite its availability. Feedback defaults to agree (232), remains append-only with safe receipt/key reuse for unchanged attempts (251–303); “request another review” accurately says it does not schedule.
- **Fix:** reuse server filters (no client-only filtering of a partial page); readable target context with exact ID secondary; local fact→evidence anchors plus publication date / Not supplied. Keep All filters initially and existing feedback default (changing default is optional). U-15/16.

**F08 optional feedback affordance (P2, not a routine-use blocker):** R:247–248 discards the retained attempt when a draft changes; R:271–272 clears it on success while R:302 leaves Record feedback enabled. Thus another unchanged click records another append-only event with a new key. This is source-confirmed behavior, not proven accidental owner use or a violation of the append-only API. Explicit new-event intent and a changed-uncertain warning are proposed optional protection (S9), not required to repair review finding/evidence. Existing unchanged uncertain retry and no-trade/no-scheduling copy remain mandatory regression gates.

### F09 — Add holding is technical; validation focus can miss the dialog field (P2; focus correction mandatory, purchase redesign optional)
- **Task/frequency:** new-lot entry; any invalid camelCase field (unitCost, costBasis, instrumentId, acquisitionDate etc.).
- **Evidence:** H:784–800 defaults **New inline instrument**, offers **Existing instrument ID**, **Account ID (optional)**, duplicate currency entry, and editable cost basis that must exactly equal quantity × unit cost (493–513). H:524 looks up validation keys such as `unitCost`, but fields use `unit-cost`, `cost-basis`, `instrument-id`, etc. Moreover H:796's `id="currency"` duplicates A:983's reporting-currency Select: the global lookup can target the outer control instead of Holding currency. Source-confirmed collision; that particular focus consequence was not browser-exercised. The existing first-invalid-field test only asserts Symbol (HoldingMutations.test.tsx:771–778), not the camelCase or outer-control collision paths.
- **Fix now:** unique dialog-prefixed IDs or scoped field refs plus real key→field focus mapping, required/input help and concrete decimal/date examples; do not weaken validation. Separate `Purchase User Journey.md` already proposes Add purchase with an authoritative lot→instrument prerequisite, exact product and safe lifetime. Do not duplicate or silently implement that unaccepted proposal, join by symbol, or invent an account picker/API.

### F10 — Activity still exposes raw machine labels (P2, optional polish)
- **Task/frequency:** reading actor/action metadata on each event.
- **Evidence:** A:389 uses the server's readable summary (good), but A:390 prints raw action/category such as `browser_user`; UTC text uses `Z` without explanation (255–258). Existing read enrichment is intentional; immutable stored events must remain untouched. No failed activity comprehension study was performed.
- **Recommendation:** optional frontend display labels + secondary technical detail and explicit timezone; retain existing readable summaries, ordering, cursor/retry/focus behavior. No new Activity filters or audit rewrite is mandatory.
